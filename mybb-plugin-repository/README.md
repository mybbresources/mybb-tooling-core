# mybb-plugin-repository

Initial Admin CP integration is implemented in `inc/plugins/mybbresources_repository.php` and `admin/modules/config/mybbresources_repository.php`. Its signed package owns only those two files; it does not copy the shared library or trust map. The installer bootstraps it as the separate `mybbresources-repository` package so later catalog updates use the same ownership record. It lists the public catalog, displays release compatibility/provenance/license/digest, and offers install/uninstall/update actions through the shared package manager. Catalog browsing follows the API's opaque `next_cursor`, preserves the active search between pages, and leaves cursor interpretation to the API. Public metadata uses a five-minute, 50-entry, 4 MiB bounded MyBB cache. Install/update release checks bypass that cache so revocation is checked against the live catalog; unavailable update checks are labeled explicitly while installed ledger and lifecycle controls remain visible. API errors preserve stable codes, retryability, and request IDs in Admin CP feedback. Downloads use the shared client, enforce the shared 64 MiB release limit and exact manifest-declared byte size, and reject redirects. Browse and installed-package tables have structured table sections and scoped column headers; search has a visible label, statuses are textual, and actions use native keyboard-operable controls. It requires the shared library installed at `inc/plugins/mybb-tooling/` and the central trusted key ring at `inc/plugins/mybb-tooling/config/trusted-keys.json`; without these it fails closed. The `mybb-tooling-core` package exclusively owns that key ring, allowing a signed overlap update to add a new key without competing manifests overwriting the trust file. The module registers a dedicated Admin CP permission, `Can manage the MyBB Resources Plugin Repository`, and checks it server-side before rendering or mutating. Package copy leaves plugins inactive. On the installed page, lifecycle controls are separate CSRF-protected POST actions restricted to unchanged plugin-role files in the signed package ledger. They invoke the shared MyBB install/activate/deactivate lifecycle helper, compatibility check, and plugin-cache update, then record active state in the ledger; deactivation does not uninstall plugin data. Uninstall also requires current MyBB activation state to be known and inactive; active plugins must be explicitly deactivated, and unknown activation state hides the uninstall action and is rejected again by the POST handler.

**Current limits:** The standalone PHP hook harness covers MyBB's `$plugins->add_hook()` registration API, permission registration, action routing, and lifecycle wiring. Signed repository package updates and live Admin CP browse/detail/install/update/uninstall flows pass against the actual Laravel catalog application and its real routes/controllers, backed by disposable SQLite/private file storage and served through fixture HTTPS, on MyBB 1.8.41 + MariaDB 11.4. The live update test verifies current/target version display and requires an explicit second review before replacing a modified file; uninstall preserves modified files and plugin data. Invalid CSRF rejection and plugin lifecycle also pass. The standalone repository CI and coordinated live fixture pass; production catalog deployment remains unverified.

The distribution reference map pins production key `catalog-2026`. The signed core package alone owns the installed central trust ring; Admin CP reads that ring. A public pin does not authenticate a PHAR download or complete publication. See [release readiness](https://github.com/mybbresources/mybb-tooling-core/blob/main/RELEASING.md) for the fingerprint, rotation process, private candidate verification, and remaining release gates.

This plugin requires the separate `mybb-tooling-core >=0.1.0 <1.0.0` package. Installation, activation, and Admin CP access check its installed version and file integrity before proceeding. Install core first; activation of the core descriptor is not required for library availability. Dependent packages prevent core removal and incompatible upgrades.

# mybb-cli

The standalone repository includes `packages/mybb-tooling`, a source snapshot of the shared package. In the coordinated workspace, `src/` is canonical; `php tools/sync-shared-package.php` refreshes the snapshot before release, and CI verifies it matches.

For local development or a standalone checkout, use `composer install` in this project; its shared tooling dependency is included under `packages/mybb-tooling/`. The coordinated workspace builds `mybb-cli.phar` together with the installer using `php -d phar.readonly=0 tools/build-phars.php VERSION [OUTPUT_DIR]` from the workspace root. Each PHAR embeds the shared library, has PHP's internal SHA-256 archive signature, and is accompanied by a SHA-256 sidecar for transfer-integrity checks. The sidecar is not an authenticity signature; only distribute a release after attaching artifacts to the project's trusted, provenance-verified release channel. V1 host support is PHP 8.2–8.4 on Ubuntu 24.04 x86_64, macOS 15 Intel, and macOS 15 Apple Silicon; Windows support is not claimed.

WP-CLI-style command line interface prototype for an installed MyBB site. It discovers the site root, validates the installation, and exposes safe administrative tasks without requiring routine manual edits or database queries.

## Command areas

- `core`: version/status and checks.
- `plugin`: list/status/activate/deactivate and repository-backed install/update/remove.
- `cache`: inspect and clear supported caches.
- `user`: password reset through MyBB's validated user datahandler.
- `config`: validate settings and report redacted configuration health.
- `db`: connection diagnostics and backups (restore is not implemented).

Commands should support human-readable and machine-readable output, useful exit codes, `--path`, and dry-run where changes are involved. The repository plugin remains the MyBB admin UI integration; the CLI should share package and compatibility contracts with it. `cache clear` removes only recognized regular `cache_*` and `datacache*` files from MyBB's `cache/` directory. It preserves `cache/plugins.php`, which the CLI reads for plugin activation state, and ignores symlinks and unrelated files.

The executable command set in `bin/mybb` includes `core status|check`, `plugin list|search|info|install|update|remove|activate|deactivate`, `user password-reset`, `cache clear`, `config validate`, and `db check|backup`. It uses the shared signature/package manager and looks for catalog keys and shared library under `inc/plugins/mybb-tooling/` in the site. `--json`, `--format=table`, `--dry-run`, `--force`, `--yes`, and `--path` are supported. Human-readable command results use a two-column table; JSON remains machine-readable. Select a site with `--path=SITE`, let the CLI discover it from the binary/current directory ancestors, or pass `--config=SITE/inc/config.php`; the last form validates the file path but never includes or executes the configuration file. `--path` and `--config` cannot be combined.

`user password-reset UID` first previews the exact numeric user ID and planned effects. Apply with `--yes --password-file=/path/to/owner-only-password.txt`; the file must be outside the site root and inaccessible to group/other users (for example, `chmod 600`). The CLI never accepts a password in argv or returns it in output. MyBB's `UserDataHandler` enforces the forum's password policy and password hashing hooks; the CLI rotates the persistent login key and deletes the user's existing session rows. The operation loads the MyBB runtime and can invoke plugin hooks.

Exit codes are `0` for success, `1` for operation failure, `2` for invalid usage, and `3` for retryable remote-service failures. JSON errors include a stable `code`, sanitized `message`, `retryable` flag, and request ID. Catalog authorization failures, not-found releases, revoked releases, validation failures, transport/TLS failures, and retryable outages retain distinct codes. Package downloads enforce the catalog's 64 MiB release limit and the signed manifest's exact declared size before returning the temporary archive.

`plugin list` inventories top-level plugin PHP files, including manually uploaded plugins. Managed package versions and file mappings come from the tooling ledger. If a safe literal `cache/plugins.php` snapshot exists, inventory can report its activation values without including or executing it. MyBB 1.8.41's default cache is database-backed, so this file may not exist; then `active` is `null` and `activation_cache` is `unavailable`. Unmanaged plugin versions are `null` because determining them would require executing plugin code or trusting undocumented metadata.

`plugin remove SLUG` returns a non-mutating review plan that separates files to remove, modified files to preserve, and already-missing files. Apply the plan with `plugin remove SLUG --yes`; before removal, the CLI loads MyBB's runtime and refuses to remove managed plugin code while active or when the activation state cannot be verified. Deactivate separately with `plugin deactivate SLUG --yes`, then review and confirm removal. Plugin data is preserved. `--dry-run` always remains non-mutating, and `--force` only removes modified files when combined with the explicit `--yes` confirmation.

`plugin install` and `plugin update` first validate and preview the signed package without changing site files or creating package state. Review the returned file map, then use the returned `next_arguments` with `--yes` to apply that exact release and site. If the plan reports destination conflicts, those files remain untouched unless you deliberately repeat with both `--force --yes`; the output lists existing files that the forced update may replace. Catalog releases are fetched and verified again on the apply invocation, and immutable signed release metadata binds the package digest and version.

The CLI updates itself through its signed `mybb-toolchain` package, which owns the installed executable and shared library. Preview with `mybb plugin update mybb-toolchain [VERSION]`, review the file plan, then apply the returned command with `--yes`. The package manager stages, backs up, and transactionally replaces the running CLI files; the current PHP process finishes using its already-loaded code, and later invocations use the updated code. No separate self-updater or independent trust path is required. The catalog must publish a `mybb-toolchain` release, or an operator can supply a locally built signed manifest and archive through the standard package update form.

`plugin activate SLUG_OR_CODENAME` and `plugin deactivate SLUG_OR_CODENAME` first display a confirmation plan. Apply with `--yes`. Managed plugin files must still match their ownership-ledger digest; a directly installed plugin can be targeted by its top-level PHP codename. The confirmed operation loads MyBB's `global.php` runtime and invokes the standard plugin compatibility and lifecycle callbacks, which may change database-backed settings, templates, or plugin data. It then updates MyBB's plugin cache and the managed package's activation snapshot. Deactivation does not uninstall the plugin or delete data. Review plugin callbacks before confirming because lifecycle callbacks execute PHP code.

Plugin activation and deactivation always load MyBB's runtime after explicit confirmation and consult its canonical cache API, even when the optional file snapshot is missing or appears unchanged. This prevents the CLI from treating a missing file as proof that a plugin is inactive. Inventory still reports unknown activation when it cannot safely inspect an optional literal snapshot.

`db check` opens the configured MyBB MySQLi write connection and reports connectivity and the count of tables matching this site's configured prefix, without printing connection details. `db backup --output=/path/outside/site.sql` streams only those tables to a new file, writes with restrictive permissions, and publishes it atomically without replacing an existing path. Add `--dry-run` to validate and preview the destination without loading database credentials or connecting. Backups inside the public site root are refused.

**Current limits:** Database diagnostics and backups support MyBB's `mysqli` driver only; SQLite, PostgreSQL, and other adapters fail with a clear unsupported-driver error. `db check`, `db backup`, signed package update, transactional self-update of the installed CLI/toolchain, and plugin lifecycle have passed against a disposable MyBB 1.8.41 + MariaDB 11.4 site. Database restore is not implemented. Plugin search/info and install/update can use the catalog; local manifest and ZIP installs are also supported. External third-party callback behavior is not verified because no upstream plugin is included. The current latest-version fixture resolved to 1.8.41, the same as the supported floor; repeat the matrix against the next supported patch after it is released.

The distribution reference map pins production key `catalog-2026`. The signed toolchain alone owns the installed central trust ring; Admin CP reads that ring. A public pin does not authenticate a PHAR download or complete publication.
